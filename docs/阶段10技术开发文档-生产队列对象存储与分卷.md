# 阶段 10：生产队列、对象存储与档案分卷

## 阶段目标

把项目档案从单机线程任务升级为可以独立部署和恢复的生产任务，把私有制品从本地文件实现扩展为 S3 兼容对象存储，并让超大项目无需下载一个不可控的大压缩包。

本阶段采用渐进式生产化：本地仍可零依赖运行，生产环境通过配置切换独立 Worker 和私有对象存储。未绑定具体云厂商，不在仓库保存任何凭据。

## 技术适配结论

- 任务执行采用数据库租约 Worker，而不是在尚未确定部署平台时强制引入 Redis。租约、领取者、重试次数和下次执行时间均持久化，API 与 Worker 可以分开运行。
- 本地 SQLite 继续用于开发；多实例生产必须使用 PostgreSQL，使条件更新和并发领取具备稳定的事务边界。
- 对象存储采用 Boto3 S3 Client。AWS S3 或提供 S3 兼容 API 的云存储可以复用同一适配器；云厂商专有 API 暂不进入业务层。
- 档案不是传统 ZIP 跨卷格式，而是多个可独立打开的 ZIP。第 1 卷始终包含正式报告和结构化记录，后续卷只包含附件，并自带分卷说明，降低单卷损坏或缺失的影响。

## 数据结构

迁移 `d61a8c4e7f20` 为 `project_export_jobs` 增加：

- `attempt_count` / `max_attempts`：已执行次数和自动重试上限；
- `lease_owner` / `lease_expires_at`：Worker 所有权与租约过期时间；
- `next_attempt_at`：指数退避后的下次可领取时间；
- `part_count`：任务生成的档案卷数。

新表 `project_export_artifacts` 为每个分卷独立记录：

- 业务类型、卷号和用户可见文件名；
- 服务端对象键；
- 字节数、SHA-256 与存储后端；
- 创建时间和所属导出任务。

旧任务表中的单对象字段暂时保留，并镜像第 1 卷，确保历史接口和迁移过程可兼容。

## Worker 状态与恢复

```text
queued
  ↓ 条件更新领取，attempt_count + 1
running + lease_owner + lease_expires_at
  ├─ 成功 → succeeded
  ├─ 失败且未达上限 → queued + next_attempt_at
  ├─ 失败达到上限 → dead_letter
  └─ Worker 消失、租约过期 → 其他 Worker 重新领取
```

默认最多执行 3 次，重试延迟为 `30s × 2^(attempt_count-1)`。人工点击“重新生成”会删除旧制品、清空租约和错误状态，并从第 1 次重新开始。

本地模式：

```env
EXPORT_EXECUTION_MODE=embedded
```

生产模式：

```env
EXPORT_EXECUTION_MODE=worker
```

```bash
cd backend
source .venv/bin/activate
python export_worker.py --purge-expired
```

API 在 `worker` 模式只创建持久任务，不启动线程池。部署平台应保证至少一个 Worker 常驻，并使用独立 CronJob 定期执行过期制品清理。

## S3 兼容私有存储

`artifact_storage.py` 提供本地与 S3 两个实现，业务任务只依赖统一接口：写入、存在性和完整性校验、删除、本地路径或短签下载。

```env
ARTIFACT_STORAGE_BACKEND=s3
ARTIFACT_STORAGE_BUCKET=private-project-archive
ARTIFACT_STORAGE_PREFIX=project-exports
ARTIFACT_STORAGE_REGION=
ARTIFACT_STORAGE_ENDPOINT_URL=
ARTIFACT_STORAGE_PRESIGN_SECONDS=300
ARTIFACT_STORAGE_SSE=AES256
```

部署环境具备 IAM、实例角色或工作负载身份时不填写静态密钥。必须使用静态密钥时，只配置在部署 Secret：

```env
ARTIFACT_STORAGE_ACCESS_KEY_ID=
ARTIFACT_STORAGE_SECRET_ACCESS_KEY=
```

上传时计算 SHA-256，并写入私有对象元数据。下载前使用 `HeadObject` 复核大小和摘要元数据，然后生成最长 1 小时、默认 5 分钟的签名 URL。Bucket 必须保持私有，并配置仅允许产品域名下载所需的 CORS 规则。

## 分卷算法

阈值由 `EXPORT_PART_SIZE_MB` 控制，默认 100 MB：

1. 先生成正式 PDF、4 份 CSV、附件目录和导出清单；
2. 估算主卷内容和附件原始大小；
3. 未超过阈值时保持单卷，兼容原有体验；
4. 超过阈值时，主卷只保留报告和结构化记录；
5. 附件按稳定顺序装入独立 ZIP，单个超大附件允许独占一卷；
6. 每卷分别上传、计算摘要、记录大小和提供下载入口。

任何一个附件卷缺失都不会阻止用户打开主卷中的正式报告和附件目录。

## API 与前端

任务响应新增：

- `attempt_count`、`max_attempts`、`part_count`；
- 仅在有效期内返回的 `artifacts` 下载清单；
- 每卷的业务类型、卷号、文件名、大小、校验状态和下载路径。

新增接口：

```text
GET /api/v1/project-export-jobs/{job_id}/artifacts/{artifact_id}/download
```

服务端仍会校验登录态、项目所有权、任务有效期、分卷归属和制品完整性。本地后端返回文件流，S3 后端返回短时签名跳转。

导出工作台在原有卡片堆叠中展示报告页数、分卷数、报告版本和完整性状态。单卷与多卷共用同一下载区域；手机端每个分卷按钮占满一行。

## 验证结果

- Alembic 从空数据库连续执行 10 个迁移并到达 `d61a8c4e7f20`；开发数据库也已升级到该版本。
- 后端 `25 passed`，覆盖单卷正式报告、强制分卷、独立下载、篡改检测、到期删除、租约回收、死信状态、旧单卷任务兼容、本地路径防穿越和 S3 元数据/短签行为。
- 前端 TypeScript、ESLint 与 Next.js 生产构建通过。
- 隔离数据库真实运行 API、独立 Worker 和浏览器：任务由 Worker 执行 1 次后成功，生成 6 页正式报告和 2 个分卷。
- 桌面与 390px 手机横向溢出均为 0；无未命名按钮、控制台错误、警告或失败网络请求。
- 两个分卷均通过浏览器实际下载并验证：主卷含 PDF、CSV 和清单，附件卷含分卷说明和原始证据。

## 当前边界

- S3 适配器已完成自动化契约测试，但没有用户云账号，因此尚未针对某一家真实 Bucket 做上传、短签和 CORS 联调。
- 报价解析任务仍使用进程内线程池；后续应复用本阶段租约模式迁移。
- SQLite 只用于本地；正式多实例部署前仍需切换 PostgreSQL 并完成备份恢复演练。
- 过期制品清理能力已有，但生产调度、失败告警和监控面板需由最终部署平台承载。
- 附件已做类型和大小校验，尚未接入恶意文件扫描服务。
